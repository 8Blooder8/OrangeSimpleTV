# v0.17 — bounded tune sessions and DRM/EME diagnostics

## Potwierdzone błędy v0.16

1. `failTuneWithDiagnostics()` wyświetlał błąd, ale nie zamykał sesji strojenia. `pendingChannelIndex` pozostawał aktywny, więc już uruchomione callbacki `evaluateJavascript()` mogły dalej uruchamiać recovery po pokazaniu ekranu błędu.
2. Callbacki nie miały właściciela w postaci identyfikatora sesji. Wynik starego kanału mógł zmienić stan nowej próby.
3. Aktywacja kanału i start mediów nie były niezależnie zatrzaskiwane. Chwilowa zmiana DOM playera mogła cofnąć automat do ponownego kliknięcia kafelka.
4. Ogólny recovery ladder zmieniał UA, cache i WebView także dla awarii wyglądających na trwały problem DRM/EME.
5. Jedna konfiguracja EME była redukowana do `WV=rejected`, bez rozdzielenia key-system/codec/robustness.
6. Na API 25 diagnostyka providera kończyła się na braku frameworkowego `getCurrentWebViewPackage()`.

To wyjaśnia obserwowane `RECOVERY#55/#56/#57`: ekran błędu był terminalny tylko wizualnie, a nie dla już wydanych operacji asynchronicznych.

## Model v0.17

Każdy wybór kanału tworzy rosnący `tuneSessionId`. Każdy Runnable i callback JS dotyczący strojenia jest akceptowany tylko, gdy należy do bieżącej, nieterminalnej sesji.

Błąd terminalny najpierw ustawia terminal state, unieważnia `pendingChannelIndex` i scheduler, a dopiero później pobiera końcowy, tylko-odczytowy snapshot diagnostyczny.

`channelActivated` jest osobnym kamieniem milowym. Gdy Orange pokaże player shell/background player dla wybranego kanału, aplikacja w tej sesji nigdy nie wraca do `activateChannel()`.

## Klasy awarii

- `DRM_WIDEVINE_UNAVAILABLE` — EME odrzuca Widevine, a Android niezależnie potwierdza brak schematu przez oba testy i `UnsupportedSchemeException` konstruktora.
- `WEBVIEW_EME_REJECTED` — Android ma Widevine, lecz WebView odrzuca wszystkie badane konfiguracje EME.
- `WIDEVINE_PROBE_INCONCLUSIVE` — wyniki natywne są sprzeczne/wyjątkowe; nie udajemy `false`.
- `WEBVIEW_EME_MISSING` — brak API EME.
- `MEDIA_SOURCE_NOT_ATTACHED` — player Orange istnieje, ale w ograniczonym czasie nie pojawia się źródło mediów.
- `MEDIA_INIT_TIMEOUT` — źródło istnieje, lecz `readyState` pozostaje 0.
- UA retry jest dozwolony tylko przed `channelActivated`, dla problemu renderowania samej strony/listy kanałów.
- Każda próba ma twardy deadline.

## Widevine na API 25

v0.17 zapisuje niezależnie:

- `MediaDrm.isCryptoSchemeSupported(WIDEVINE_UUID)`,
- `MediaDrm.isCryptoSchemeSupported(WIDEVINE_UUID, "video/mp4")`,
- sukces/`UnsupportedSchemeException` z `new MediaDrm(WIDEVINE_UUID)`,
- vendor/version/description/algorithms,
- vendorowe `securityLevel` i `systemId`, jeśli firmware je udostępnia.

Wynik „definitywnie unsupported” wymaga zgodności wszystkich tych sygnałów; zwykły wyjątek nie jest już zamieniany na `false`.

## WebView API 25

Frameworkowe `WebView.getCurrentWebViewPackage()` jest API 26+, więc na API 25 zapisujemy realny domyślny User-Agent/wersję Chromium oraz kandydatów PackageManager (`com.google.android.webview`, `com.android.webview`, Chrome i standardowe warianty). Kandydaci nie są przedstawiani jako pewny aktywny provider.

## Macierz EME

Bez tworzenia sesji kluczy badane są niezależnie: minimalny key-system, AVC baseline/main/high, AAC, AVC+AAC oraz `SW_SECURE_CRYPTO`, `SW_SECURE_DECODE`, `HW_SECURE_CRYPTO`, `HW_SECURE_DECODE`, `HW_SECURE_ALL`. Każdy wiersz zapisuje accepted/rejected/exception oraz nazwę/komunikat błędu.

## Observe-only media

Podczas diagnozy v0.17 nie wywołuje bezpośrednio `video.play()`, `video.load()`, nie zmienia `src`, MediaKeys ani geometrii video. Orange pozostaje właścicielem MSE/EME. Dopuszczone jest wyłącznie użycie prawdziwych kontrolek Play/Expand Orange przez wcześniej potwierdzoną ścieżkę wejścia natywnego.

## Diagnostyka sieci i JSON

`shouldInterceptRequest()` zapisuje tylko host/path interesujących żądań (`.mpd`, `.m3u8`, manifest/license/licence/widevine/drm`). Query stringi, headers, cookies, Authorization, challenge/response i media bytes nie są zapisywane.

Terminalna sesja zapisuje `ostv-diagnostic-session-<id>.json` w app-specific external files z informacjami o urządzeniu/API, realnym i aktywnym UA, provider candidates, natywnym DRM, EME/MSE/media, przejściach state machine i sanitizowanych logach.

## Build

Pozostaje istniejący szybki build bez Gradle i z trwałym cache: AAPT2 → javac → D8 → zipalign → apksigner.
