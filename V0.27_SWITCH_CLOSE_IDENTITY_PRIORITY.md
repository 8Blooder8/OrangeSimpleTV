# v0.27 — DIW377 switch close / identity / priority fix

## Root cause confirmed by decoder diagnostics

The v0.26 failure trace requested `Cartoon Network HD` from a stable `Music Box Dance` player, but never reached `TARGET_TILE_ACTIVATE`. It emitted `OLD_PLAYER_CLOSE_REQUEST`, then `OLD_PLAYER_CLOSE_TIMEOUT`, and rolled back while the old expanded blob player was still rendering.

Orange renders two buttons with the same `ClosePlayerButtonWrapper` styled-component class:

1. `player_back` — back arrow,
2. `player_close_X` — actual X close.

v0.26 used `querySelector(...)`, therefore it selected the first/back button. Its React handler returned successfully, but it did not unmount the player container.

## v0.27 fixes

- `officialPlayerCloseButton()` resolves the actual X by `player_close_X`; structural fallback is the last of multiple close-wrapper buttons, never a lone ambiguous button.
- close is retried through the same official Orange X handler after 420 ms, at most twice; total close deadline is 1400 ms.
- channel activation returns the resolved card name/id. Java refuses to send a native tap if the resolved identity differs from the requested channel (`CHANNEL_IDENTITY_MISMATCH`).
- tune work pauses EPG/metadata enrichment (`setTunePriority(true)`) so a guide scan cannot delay a channel switch.
- if the React pass already has complete programme timing, same-origin resource replay is skipped entirely.
- success diagnostics no longer call the heavy full `uiDiagnostics()` on the critical path; they snapshot only `pageState()` + `playerUiState()`.
- delayed live-edge callbacks are rejected if another tune session has already started.
- opening the guide releases tune priority so unfinished metadata work can continue; closing it restores playback priority.

No direct `video.src`, MediaKeys, MediaSource, DRM or DOM-player removal is used. The close operation remains the official Orange UI handler.
